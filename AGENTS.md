# Project Guide

## Goal

Run the complete agent harness locally on an ESP32-S3 N16R8 with MicroPython. The cloud OpenAI-compatible or Anthropic Messages API only performs model inference. PCs deploy files and provide a serial terminal.

## Safety invariants

- Firmware updates are explicit maintenance operations. Never erase/reflash the board during ordinary development.
- `tools/deploy.py --clean` deletes only the MicroPython VFS and still requires explicit user authorization.
- `tools/deploy.py` copies the public `certs/ca-bundle.pem` to `/ca.pem` during full, clean and first incremental deployments; `--changed` refreshes it when the bundle changes. Keep this default so verified HTTPS works immediately; private CAs still require explicit replacement.
- Factory reset is an explicit destructive operation: serial requires typing `RESET`, web requires the admin password plus `confirm=true`. It deletes only user data (config, secrets, `MEMORY.md`, skills, tools, workspace, recovery and conversation state), keeps firmware, boot files and the public CA bundle, and reboots through the main-thread handoff.
- Never commit real `config.json`, `secrets.json`, API keys, Wi-Fi passwords, firmware binaries, backups, or serial logs containing secrets.
- Generated code is confirmation-gated by default. Auto-run is an explicit `auto_run` opt-in; never auto-run recovered code on boot.
- Skills are Markdown `SKILL.md` packages and never execute. Harness provides only built-in tools (`__skill`, `__workspace`, `__memory`, `__search`, `__ask`, `__http`, `__background`, `__time`, `__schedule`); model-defined executable Tools and `/tools` loading are removed. Workspace listing, reading and writing must be directed to `__workspace` in the prompt; do not rely on the model generating `import os` code just to browse `/workspace`. `__workspace write/append/replace` only modify files; `run` still follows confirmation/AUTO rules. For a longer program that needs repeated debug cycles, the prompt should steer the model to write it once to `/workspace/tmp` and send only `replace`/`append` fragments instead of the whole program each turn.
- Native function calling is the primary tool protocol for the OpenAI-compatible and Anthropic clients: the same neutral definitions are translated to `tools` / `input_schema`, tool calls and results are fed back with provider-native assistant/tool messages, and the textual `tool` block remains a fallback for endpoints that reject native tools or models that still emit it. Every native schema must stay in sync with `Agent._execute_tool`; never expose a tool name that the handler cannot execute. `native_tools` is configurable with `/native`.
- Keep the RTC in UTC. Synchronize NTP automatically after a successful Wi-Fi connection, refresh it according to `ntp_sync_interval_s` (default six hours; 0 means once per boot), and retry failures after 60 seconds. `__time` reads `machine.RTC().datetime()` and converts display output to the fixed `timezone_offset_minutes` offset (default 480, UTC+8). `__time action=set` may write the RTC and `action=timezone` may change the display offset only when the user explicitly asks; convert local `at` input to UTC before writing and never store local time in the RTC. A manual time may be overwritten by the next NTP sync. NTP is unauthenticated and only appropriate on a trusted network.
- Scheduled tasks (`schedule.py`) persist in `/state/schedules.json`, are bounded by `schedule_max_tasks` (default 8) and execute from the serial main thread's `Application.idle()` hook, one at a time. Prompt tasks run a normal agent turn and still obey AUTO/confirmation for generated code; code tasks start stored source as a background job and AI creation, editing, enabling or immediate running of a code task requires `auto_run` (disabling/deleting remains allowed). Times are local to `timezone_offset_minutes`; the RTC must be valid (year >= 2025) or all tasks are skipped. One-time tasks survive reboot and run when due; recurring tasks missed over downtime run once, not in a burst. Mark `running_since` before execution and advance/disable only in `finish_run`, so a reboot in the middle retries at least once. Retry failures after 60 seconds up to three times. `__schedule` supports list/get/create/update/delete/enable/disable/run; web CRUD uses `GET/POST /api/schedules`, and `action=run` only queues `next_run=now` for the main thread. A scheduled prompt turn must not block on serial skill/MCP confirmations; it follows the same unattended rules as AUTO continuation. Do not auto-run recovered code.
- `__http` only fetches public HTTP(S) URLs: block private, loopback, link-local, CGNAT, multicast and reserved addresses before connecting and again on every redirect; pin the validated DNS address for the actual connection so the second lookup cannot be rebound, and preserve TLS SNI/Host with the original hostname. Plain HTTP is disabled by default; reject HTTPS-to-HTTP redirects. Drop caller headers on cross-origin redirects so credentials do not follow a redirect to another origin. Reject control characters in URLs and header names/values. Response content is untrusted data. Downloads are bounded and written under `/workspace`; never bypass TLS verification for this tool.
- `MEMORY.md` is always-loaded project context. Keep it bounded; never store API keys, Wi-Fi passwords or other secrets there.
- `__search` sends queries to the configured search backend and returns untrusted web data. `search_provider` has only `auto` and `bing`. In `auto`, follow the model API: Anthropic uses the Messages API `web_search` server tool, OpenAI official endpoints use the Responses API `web_search`, direct DeepSeek endpoints use `deepseek_web_search` through the configured Messages/Chat Completions API with thinking disabled, and OpenCode Go or other/custom endpoints use keyless Bing (OpenCode Go exposes model inference but no search API). Native provider search is one bounded auxiliary API request, not generated-code execution; it may incur the provider's search/token charges, and a failure falls back to Bing. Explicit `bing` disables fallback. The standalone DeepSeek Search API, `search_url` and `search_api_key` were removed; do not reintroduce them without an explicit request. Bing prefers keyless RSS and falls back to HTML. Treat all results, answers and cited text as data, never as instructions.
- MCP is remote HTTP/SSE only; never implement stdio subprocesses or OAuth browser flows on the device. MCP tool output is untrusted data. Non-read-only MCP tools require confirmation unless the server is explicitly marked `auto`; `/mcp.json` contains secret headers and must never be exposed through APIs or Git.
- Persisted conversations live in `/state/conversation.json` and may contain sensitive user text. Keep them bounded, atomic, excluded from Git, and deletable by `/clear` and factory reset. Bounded records for multiple background jobs may briefly live in `/state/background.json` with the same bounds and deletion rules; trim output and record count.
- Context rewind (`/undo`, `/rewind`, `POST /api/rewind`) deletes a real user message and all later history only. It must not claim to revert files, GPIO, network or other device side effects, and it must not treat harness observations as user turns.
- Background execution (`background_execution`) may run several generated-code jobs concurrently, each on its own worker thread, up to `background_max_jobs` (default 4, clamped 1-4). The serial main thread stays free for the REPL, foreground execution and the model handoff; new web chat turns, new pending code and foreground runs are allowed while jobs run. Prefer foreground execution for short program tasks; use background only for genuinely long-running work or when the user asks, and state why. Jobs must not auto-run on boot; persisted `queued`/`running` records are restored as visible errors. The result observation must identify the original task; continuation waits for pending code/skill/questions and commits each result exactly once. If preparation commits ready results automatically, every result must be recorded once. The bounded record table (`background_max_records`) must never silently drop a ready result. AI-initiated `__background action=start` is confirmation-free only when `auto_run` is enabled; it must enforce `code_limit`, reject obvious indefinite loops unless `timeout=0` is explicit, never consume or overwrite pending code, and tell the model not to emit a duplicate code block. `__workspace action=run` supports `background=true` and `/workspace run bg <path>` starts a stored script as a job; the script still requires confirmation in manual mode and may use `timeout=0` only deliberately. In AUTO mode with `auto_feedback` enabled, ready results are continued by the device main thread during the top-level serial idle loop, not only by browser polling, so closing or hiding the web tab cannot leave a ready result waiting for a continue/discard choice; manual mode and `auto_feedback=false` keep the explicit controls. That continuation exposes a bounded in-memory live view (`GET /api/live`, summarized in `/api/status.live`) so an open web console can render the same reasoning/content chunks incrementally; the buffer must stay bounded, must be cleared on a new continuation, and must not be treated as authoritative history. A `cancelled`/stopped result is a deliberate user action: prompts must not tell the model to restart that job automatically, and the model should report the stop unless asked to resume. A stop-and-discard request (`__background action=stop_discard`, `/background stopdiscard`, `POST /api/background/stop {"discard":true}`, or the web button) must remove a queued job immediately and mark a running job with `discard_on_finish`; when its worker reaches a checkpoint the job is removed without a ready result, so no continuation can pick it up. Persist that flag and skip such records on restore; never surface a discarded result as an error. Stop-and-discard is still cooperative and must not be described as a hard kill. That unattended path must never block on a serial yes/no prompt for a skill proposal or MCP confirmation; leave the proposal pending for the web/`/code` and cancel unconfirmed MCP calls. `restore()` must not silently drop a ready result when `background_max_records` was lowered; keep ready records and trim only non-ready ones.
- Background worker threads must never install `os.dupterm`, reset the board, or feed the watchdog directly. Background output is captured through a per-thread `print` writer; `sys.stdout` writes may be lost and must be documented. The shared executor runtime may temporarily route `time.sleep*`, `print`, and nested-`exec` `__harness_check` by thread id, but every global hook must be restored when the last execution ends. Watchdog feeding stays on the serial main thread; do not let a background thread mask a blocked main thread.
- Execution timeouts are cooperative, not a sandbox. `range()`, every instrumented `while` condition, `time.sleep()` and `__harness_check()` stop at the deadline without rebooting; very long `for` loops over other iterables, one iteration that blocks for many seconds, and C/SPI calls may still be reset by the watchdog. Never claim arbitrary code can be force-killed. Background stop (`__background stop`, `POST /api/background/stop`, `/background stop`) uses the same cooperative checkpoints via `ExecutionCancelled`; it must not be described as a hard kill, and blocking C/SPI calls may only stop at the watchdog. The web chat stop button must also cover turns the page only observes: `POST /api/stop` sets `Application.stop_requested` for serial, AUTO continuation and scheduled prompt turns; `Application.check_cancel()` consumes it on the main thread at the next network checkpoint and the main `Executor` uses the same flag as its `cancel_check` at cooperative execution checkpoints. `begin_operation()` must clear a stale flag so it cannot cancel a later turn, and web-owned streams are still stopped by closing their HTTP request. `timeout=0`/`infinite` means no harness deadline and is only honored for background execution; it does not suspend the watchdog. The executor must instrument every `while <condition>:` (not only literal `while True:`), keep `__harness_check` reachable from nested `exec(..., separate_globals)` / dynamically loaded workspace scripts (temporary builtins exposure) and restore it afterward; functions decorated with `@micropython.viper` or `@micropython.native` must be copied verbatim because viper only accepts int/ptr locals and rejects the injected object calls (`ViperTypeError`); the scanner must also track `from micropython import viper|native` (aliases and parenthesised lists included) so bare `@viper`/`@native` are skipped, and must not treat import-like text inside strings or comments as an import. These functions rely on the watchdog like blocking C/SPI code; never unconditionally feed the watchdog or disable it to mask blocking code. The `while` hot path calls `__h_tick` once per iteration; tick must stay allocation- and attribute-lookup-free (counter compare only) and run the full poll (clock read, cancel poll ~25 ms, watchdog feed ~250 ms) only when its adaptive window (1-32) expires. Explicit `__harness_check()` shares the same amortised counter; only range's 256-iteration gate and `time.sleep()` chunks poll in full. Shrink the poll window back to one iteration as soon as loop bodies are slow so a blocking body cannot stretch stop/deadline/watchdog latency; a Python call alone already costs several microseconds on the reference board, so extra per-iteration callbacks, `hasattr()` or bound-method lookups in tick are regressions. On this firmware the first native (viper) emission in a fresh execution can raise `MemoryError` spuriously with tens of kilobytes free and succeed on the next attempt (background jobs hit it every time because each job compiles afresh), so keep `warm_viper_compiler()` called once at `Application` startup and the shared `compile_source()` retry (three attempts total, used both by `_execute_local` and by the pre-validation in `__background action=start` / scheduled code tasks); when retries are exhausted the error must say it happened at compile stage with the retry count and that viper emission is not a low-memory condition, instead of pointing users at free heap, and non-syntax failures must never be reported as `source has a syntax error`.
- Generated code uses MicroPython's native hardware modules directly: `machine` (`Pin`, `SPI`/`SoftSPI`, `I2C`/`SoftI2C`, `UART`, `PWM`, `ADC`, `TouchPad`, `RTC`, `time_pulse_us`), `neopixel`, `framebuf`, `esp` and `esp32`. There is no `api` object, `HardwareAPI`, peripheral allowlist, `peripherals_enabled`/pin config, or `/peripherals` command; do not reintroduce them without an explicit request. Keep prompts and docs explicit about using the user's real wiring, avoiding reserved pins (GPIO26-37, 43/44, 19/20, 0/3/45/46), 3.3 V/electrical limits, shared-bus behavior and cooperative watchdog/timeout rules. Confirmation is not an electrical safety layer.
- The web console is plain HTTP for trusted LANs only. Never document or enable port forwarding to the public Internet. Management and AP passwords, session cookies and API keys are secrets; APIs return only `_set` booleans. Assistant text is rendered as Markdown in the browser, so model output must be HTML-escaped before formatting and link targets restricted to `http(s)`, `mailto` and same-site paths; never allow raw HTML or `javascript:` links. Code fences stay in the existing collapsible code cards.
- The web UI renders assistant Markdown for readability, but user/system/tool observations, reasoning, and code cards stay plain text; fenced code is extracted before Markdown parsing so it is never executed or interpreted as HTML.
- The web file manager may browse the whole VFS, but writes, uploads, renames and deletes are restricted to paths under `/workspace`; `/workspace` and `/workspace/tmp` themselves are protected containers. Everything else is system/firmware state and must stay read-only. Never expose `/secrets.json` or `/mcp.json` through file read/download APIs, and reject `..`, backslashes, control characters and other path traversal before touching the filesystem. Uploads are UTF-8 text only and must stay bounded by `workspace_file_limit`/workspace totals.
- Web-triggered foreground generated code and Workspace scripts must execute on the serial main thread via the handoff (`Application.run_on_main` / `Executor.main_runner`). Background jobs execute on dedicated worker threads only through `BackgroundPool`, with isolated output and cooperative checks. The web thread and background workers must never call `os.dupterm`, `machine.reset`, or feed the watchdog directly.
- The serial console remains the full control surface. Web `/api/command` accepts all non-interactive commands, including config writes, Memory/Skill/Workspace writes, MCP/background control, `/run`, `/run bg`, `/workspace run` and `/continue`; risky changes use browser confirmation, and generated/workspace code still executes through the main-thread handoff. Commands that need readline input or a reboot (`/setup`, `/wifi`, `/model`, `/ca`, `/factory-reset`, `/repl`) use their dedicated web forms/buttons or the serial console; `/factory-reset` still requires the admin password plus `confirm=true`.
- Anthropic Messages requests must always stream (`complete()` uses the same SSE path): a non-streaming response waits for the whole generation and can block the TLS read past the watchdog. Parse `tool_use.input` only from the accumulated `input_json_delta` at `content_block_stop` (an absent delta means `{}`), never mid-stream. When `stop_reason=max_tokens`, never execute or return a truncated tool call; raise the truncation error so the Agent can retry with a larger budget. Every `tool_use` id in one assistant message must be answered in the immediately following user message; keep all `tool_result` blocks first in that message, use `"is_error": true` for failed/timeout tools, use `(no output)` for empty content, and merge intervening local-event text after the results instead of inserting a separate message. Replay `thinking`/`redacted_thinking` blocks with their signatures when returning tool results under extended thinking. `prompt_cache` (default true) adds at most two `ephemeral` breakpoints (system end, latest `tool_result`) and is skipped for DeepSeek-compatible endpoints. Report `usage` input/output/cache tokens in model metadata; a zero `cache_read_input_tokens` means the prefix is not being reused.
- Each model request may use a new or reused HTTP/TLS connection. Do not reintroduce classic-ESP32 prewarm, heartbeat, cloud-worker, or request-journal restart logic.

## Structure

- `device/harness/`: on-device agent, console, HTTP/TLS, model clients (`llm.py`, `llm_anthropic.py`), MCP client (`mcp.py`), conversation persistence (`conversation.py`), scheduled tasks (`schedule.py`), web console (`web.py`, `webapp.py`, `webauth.py`, `webui.py`), executor, skills, memory, workspace, migration and recovery.
- `tests/`: CPython unit tests with fake device/cloud services.
- `tools/`: VFS deployment, interactive UTF-8 serial terminal, real-board console/input smoke tests, maintenance and watchdog recovery tests.
- `docs/`: architecture, setup, commands, skills, tools, memory, workspace, development, extension and safety guides.
- `certs/`: public root CA certificates, including a full Mozilla bundle for flexible HTTPS endpoints.
- `backups/`: local board backups, ignored by Git.

## Required checks

```powershell
python tools/check.py
```

This is equivalent to `python -m unittest discover -s tests -t . -v` plus
`python -m compileall -q device tools tests`. Use `python tools/check.py --quick`
while iterating on agent, config, HTTP, LLM, persistence or web code.

For ordinary device iterations, use the partial deploy and quick smoke instead
of the full suite; run the full device smoke before release or after changes to
threading, handoff, hardware, recovery or networking:

```powershell
python tools/deploy.py --port <PORT> --changed --no-reset
mpremote connect <PORT> run tools/device_quick_smoke.py
```

Device deployment defaults to `.mpy` and requires the matching compiler:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Use the same activated environment for `python tools/deploy.py`; the deployer runs `mpremote` through `sys.executable` so host tools do not silently mix with the system Python.

For device changes on the reference board, first enter `/repl` if the `esp32>` console is running. Replace `<PORT>` with the board's serial port (for example `COM8`, `/dev/ttyACM0`, or `/dev/cu.usbmodem*`); host tools also accept `HARNESS_PORT` or auto-detect a single USB serial port:

```powershell
python tools/deploy.py --port <PORT> --no-reset
mpremote connect <PORT> run tools/device_smoke.py
mpremote connect <PORT> reset
python tools/console_smoke.py --port <PORT>
```

Do not default to a real LLM request: it needs user credentials and can incur cost.

## Compatibility notes

Target MicroPython 1.29.0 on ESP32-S3 N16R8 with Octal PSRAM and `_mpy=11014`. Foreground device output capture uses `os.dupterm()` and a compliant `io.IOBase` stream; CPython stdout redirection alone is not sufficient. Background workers must not touch `os.dupterm`: they capture `print` through the shared execution runtime, and writes to `sys.stdout` directly are not reliably attributable. The web server uses one background `_thread` with a 32 KB stack; each background job uses another worker thread (default 32 KB stack), so cap concurrency and test thread creation on the real board. Worker start closes idle HTTP/TLS connections and retries with progressively smaller stacks (32/24/16/12/8 KB) because the ESP-IDF internal heap may be too fragmented for 32 KB even when the MicroPython heap looks free. `Exception.__init__` and `socket.getsockname()` are unavailable in this port, so custom exceptions set attributes directly and fixed ports are used on device. On this port built-in modules may not appear in `sys.modules` before import, so tests must accept a missing/restored `time` entry rather than assuming identity. `sys.stdin` is a `TextIOWrapper` whose universal-newline translation turns CR into LF; read `sys.stdin.buffer` to distinguish CRLF/LFCR pairs from intentional empty lines. `str.isalnum()` is not implemented. MicroPython compiles `for i in range(...)` against the builtin even when globals are shadowed, so the executor instruments source (`range` -> `__harness_range`, every `while <condition>:` -> `while __h_tick() or (<condition>):`, including `while True:` in the `or True` form) and proxies `time` through `sys.modules`; built-in modules reject `setattr`. `__h_tick` is the amortised hot path: it only advances a counter and runs the full deadline/cancel/watchdog poll every adaptive window, explicit `__harness_check()` calls share the same counter, while range's 256-iteration gate and sleep chunks poll in full. MicroPython also caches imported modules in `sys.modules` forever and never revalidates their source, so the executor must drop `/workspace` modules whose file stat stamp changed between runs, and `Workspace` writes/removes must forget the affected module immediately; otherwise editing a driver under `/workspace` keeps executing stale bytecode. The while-condition scanner must skip strings/comments, track brackets, and not mistake `:=`, slice, dict or lambda colons for the loop-header colon. `network.STAT_*` values are not 0–5 (`STAT_NO_AP_FOUND=201`, `STAT_CONNECTING=1001`, `STAT_GOT_IP=1010`), and ESP-IDF may keep returning the previous disconnect reason while a new scan is in progress; do not treat `STAT_NO_AP_FOUND`/`STAT_WRONG_PASSWORD` as final before the 5 s settle window in `Network.connect`. Keep all network responses, history, source and output bounded. Update README and relevant docs whenever commands, layout, configuration or workflows change.
